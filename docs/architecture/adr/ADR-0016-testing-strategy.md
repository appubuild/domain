# ADR-0016 — Test pyramid with generated media fixtures, never committed

**Status:** Accepted · **Date:** 2026-09-24 · **Deciders:** Architecture Group

## Context

Media software is notoriously hard to test: fixtures are large binaries, real codecs are
needed for realism, GPU paths need hardware, ASR needs model weights, and "correct" is often
a perceptual judgement. A team that cannot test the editor will not refactor it, and a
codebase that is not refactored for ten years dies.

Constraints we accept as facts: CI machines have no GPU and no downloaded models; committing
`.mp4`/`.bin` fixtures bloats the repository permanently (git never forgets); and flaky
media tests get disabled, which is worse than not having them.

## Decision

### Pyramid

| Level | Scope | Runtime target | Dependencies |
| --- | --- | --- | --- |
| **Unit** (≈ 75%) | pure domain, core, services with fake ports | < 5 ms/test | none |
| **Integration** (≈ 18%) | multiple modules, real SQLite in tmp, real event bus, API via `httpx` ASGI transport | < 200 ms/test | none native |
| **Media** (≈ 5%) | real encode/decode/composite/export via PyAV & the static FFmpeg binary | seconds | PyAV, imageio-ffmpeg |
| **ASR** | transcription with a real small model | tens of seconds | model weights (opt-in) |
| **GPU** | backend parity + capability probes | seconds | GPU (opt-in) |
| **UI** | component + interaction tests, timeline canvas behaviour | < 1 s/test | Node, jsdom/happy-dom |
| **E2E** | scripted product flows against a live backend | minutes | Node + backend |
| **Perf/Stress** | benchmarks with budgets vs a baseline file | minutes | opt-in, nightly |

Markers map 1:1 to `pyproject.toml`'s pytest markers. The **default** run is
`pytest -m "not (asr or gpu or perf or slow)"` so a contributor on a laptop with no GPU and
no models gets a green, fast suite.

### Media fixtures are generated, not committed

`tests/media/synth.py` builds deterministic assets with PyAV at session scope:
a 3 s 640×360 30 fps H.264+AAC clip with a **known frame pattern** (frame index encoded in
pixel values so tests can assert exactly which frame was decoded), a variable-frame-rate
clip, an audio-only WAV with a known sine, a PNG sequence, and a 10 s clip with deliberate
silence gaps for VAD tests. Generation is cached in a session-scoped tmp dir and reused
across tests. **Nothing binary is committed**; `scripts/check_repo_hygiene.py` fails CI if a
binary over 64 KiB appears in the tree.

This gives realism (actual H.264 GOPs, actual AAC frames, actual seeking behaviour) with a
repository that stays small. It also means fixture properties are *known* — we can assert
"seek to frame 45 returned frame 45" rather than eyeballing output.

### Property-based invariants

Some invariants must hold for *all* inputs, so they are tested as properties with generated
inputs (Hypothesis-style generators implemented in-house to avoid a heavy dependency):

* `Timecode ↔ frames` round-trip for every supported rate, including drop-frame.
* Command round-trip: for every registered command, `execute → undo` yields a byte-identical
  serialised project (ADR-0008 §Consequences).
* Document ↔ table round-trip: for generated timelines, save → load → save is identical
  (ADR-0004).
* Caption pipeline determinism: same transcript input → byte-identical `CaptionDocument`.
* Compositor determinism: same `(timeline, t)` → identical frame hash, twice, in any order.

### Golden frames, with tolerance

Rendered output is compared against golden hashes stored as **JSON** (hash + tolerance +
generator version), not as committed images. Goldens are regenerated by an explicit,
reviewed command (`make goldens`) that prints a diff summary; a golden change in a normal PR
fails CI, because it usually means an unintended visual regression.

### Frontend tests

* ViewModels (store actions) are tested as pure functions against a mocked transport —
  the highest-value frontend tests, covering optimistic update + reconciliation + rollback.
* Components are tested for behaviour (interaction → store action dispatched), not for markup.
* The timeline canvas is tested via a headless canvas recorder that captures draw calls,
  asserting structure ("clip drawn at x=…, width=…") instead of pixels.
* `tsc --noEmit` with `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`
  is a hard gate — a large class of runtime bugs is prevented at compile time.

### Performance budgets

`docs/architecture/performance-budgets.md` defines numeric budgets. `scripts/bench_*.py`
measures them and writes a JSON report; CI compares against the committed baseline and fails
on regressions beyond the stated tolerance. Perf runs are opt-in/nightly so they never make a
PR red for an unrelated machine-speed reason, but the baseline is reviewed monthly.

## Consequences

**Positive**

* The suite is fast and runs anywhere, so people actually run it.
* Real codecs are still exercised, so media bugs are caught.
* Property tests catch whole classes of drift bugs that example tests miss.
* The repository stays small forever; no LFS, no binary churn.

**Negative / accepted**

* Fixture generation costs a few seconds on first run per session. Acceptable, and cached.
* ASR and GPU paths are not covered by default CI. Mitigated by dedicated opt-in jobs
  (a GPU runner and a model-cached runner) that run nightly, and by the fact that everything
  downstream of transcription is testable without a model (ADR-0009).
* Golden-hash comparisons can be sensitive to library upgrades (NumPy/OpenCV changing a
  rounding). Mitigated by recording generator/library versions in the golden metadata and
  regenerating deliberately.

## Alternatives considered

| Option | Rejected because |
| --- | --- |
| Commit `.mp4`/`.wav` fixtures | Permanent repository bloat, LFS complexity, unknown fixture properties |
| Mock all media I/O | Would not catch the bugs that actually ship (seeking, GOPs, colour conversion) |
| Snapshot-image comparison | Large binaries, brittle across platforms, unreviewable diffs |
| 100% coverage target | Incentivises meaningless tests; we target coverage on `core/domain/services` and behaviour coverage elsewhere |
| Test only in the browser (E2E-heavy) | Slow, flaky, and cannot express frame-level assertions |
