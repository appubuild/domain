# Local project copies — Phase 4 partial

The browser implementation uses IndexedDB through an asynchronous `ProjectRepository` interface. Schema version 1 stores a UUID project ID, name, creation time, CRS84, display units and GeoJSON features with UUIDs and drawing modes. Zod validates the schema and the survey engine checks each geometry before write and after read. Project names entered through create, import, rename and duplicate are trimmed before validation. Stored or backup records with leading or trailing whitespace in a name are rejected rather than silently normalized: existing such rows remain untouched and are flagged unreadable, and a backup containing one cannot be restored. Earlier application-generated records were saved with trimmed names; externally authored records may need separate investigation, not storage clearing. Editor-only properties are removed. Limits are 100 features and 2,000 vertices per feature. The IDB `add` operation is atomic and rejects duplicate IDs rather than overwriting data. Delete is separately confirmed and atomically compares the complete validated record against the version shown before deleting; a stale or missing copy is not removed.

Saving always creates a new named copy; it does not update earlier copies or autosave edits. A copy is opened only into an empty editor to avoid replacing unsaved work. Opening switches both the drawing engine and toolbar to selection mode, so a previously chosen drawing tool cannot silently add a feature when the user intends to select one. If Terra Draw rejects an added feature, the empty editor is cleared and the stored copy is untouched. The workspace can export a saved project as RFC 7946 GeoJSON, download a versioned JSON backup of all saved copies, or download a compatible single-copy backup. Restore validates every record before an atomic transaction; it rejects the entire backup if any project ID already exists, with no overwrite. All-copy backups are limited to 100 projects and 10 MiB and do not include unsaved editor changes. Each individual backup is also limited to 10 MiB. The per-copy option can help if the full collection exceeds its limits, but a single copy exceeding 10 MiB cannot be backed up with this mechanism. GeoJSON import accepts a bounded RFC 7946 FeatureCollection with 2D points, lines and single-ring polygons. It validates all geometry before creating a separate project; imported IDs and properties are discarded and new IDs assigned. Explicit CRS declarations, unsupported geometry, invalid coordinates and antimeridian crossings are rejected. Coordinates within range cannot prove the source CRS: users must verify that their source is WGS84 longitude/latitude; no reprojection is performed. Import requires an explicit user confirmation, which resets when a different file is selected or import succeeds. The confirmation records user intent, not a technical verification of the source. Saved project copies can be renamed with a full-record stale-write check and duplicated with new project and feature IDs only if the complete source snapshot still matches in the same transaction as the insertion; geometry edits still save as a separate copy rather than replacing the original. Attachments, plot names and richer project metadata are not implemented. The stored format is versioned but no migration beyond the initial schema is implemented. Records that fail the current schema, including unknown future versions, are preserved in IndexedDB and flagged as unreadable; valid records remain available. The all-copy backup is disabled whenever unreadable records are detected, and its strict re-read also fails if an unreadable record appears after the list was loaded. Readable copies can be backed up individually. A read-only diagnostic can export currently unreadable records as JSON only when all values are faithfully representable as JSON and the export fits the limits (100 records, 10 MiB, bounded depth and complexity). Unsupported types, shared references, cycles and oversize data cause the whole diagnostic to fail rather than being silently coerced or omitted. The diagnostic is unencrypted, contains raw data, is not a restorable backup and is rejected by the normal restore function. This release has no tool to repair, migrate, restore or delete unreadable records; do not clear browser storage in an attempt to fix them. IndexedDB availability, quotas and browser eviction vary; local copies are not encrypted against someone with access to the browser profile. Exported backups also contain unencrypted land data and must be stored securely. The browser download cannot be verified by the application as safely retained; users should verify and keep a separate backup. GeoJSON import, backup checking and restore decode files as strict UTF-8, rejecting malformed byte sequences instead of silently inserting replacement characters; legitimate U+FFFD text is preserved. A separate non-destructive backup check validates a selected file against the same format, size and geometry rules without writing to IndexedDB. It also checks for matching project IDs in a single read-only transaction and reports conflicts or an unavailable check; the result is a point-in-time preview, not a reservation. Other tabs can change data before restore, so restore still rejects conflicts atomically. The check cannot detect all tampering, prove authenticity, verify file retention or guarantee a later restore will succeed; test recovery separately and keep copies securely.

Repository and UI tests use fake-indexeddb. Headless Chromium exercises real MapLibre/Terra Draw save/reopen, edited-polygon persistence, backup/export and GeoJSON import. A headless Chromium two-tab test confirms a stale delete fails after a concurrent rename and the newer copy remains. A cancelled restore and a batch containing a conflicting ID were also tested in Chromium; no project was added or overwritten after reopening the page. A Chromium test also downloads and restores one copy, checks its full record and confirms a second copy remains unchanged. Quota-exhaustion, private-mode, other browsers, Electron and Android storage and transfer are not verified. The UI project list does not synchronize live across tabs; use Refresh saved copies to reload it. Opening or downloading a single listed copy compares the latest valid stored record with the displayed snapshot; if changed, missing or unreadable, the action is rejected and the user is asked to refresh. This is a point-in-time read, not a lock on future changes. Rename, duplication and delete atomically compare the complete validated snapshot against the current record; a same-name replacement with different geometry is rejected. An ABA change that returns the entire record to identical values cannot be detected without a revision or tombstone scheme. Production deployment needs an explicit data retention, backup, recovery and migration plan before relying on this for important records.


## Report status and font

An experimental English PDF report can be generated from saved copies with ASCII-only project names and at most 5,000 coordinates. It contains spherical estimate totals, per-geometry measurements and schematic diagrams, without claiming a scale or cadastral accuracy. The report language selection is independent of the UI language. It uses pdfmake with the locally bundled Noto Sans Bengali font from Google Fonts (source `ofl/notosansbengali/NotoSansBengali[wdth,wght].ttf`, Git blob `25e13e26dc15c4933f8fe49c9efcda54152349db`); its SIL OFL license is included in `packages/reports/assets/OFL.txt`.

Bengali PDF downloads are **disabled**: the automated PDF.js extraction test shows Bengali characters in visual rather than logical Unicode order, e.g. `ভূিম` instead of `ভূমি`. English reports also reject non-ASCII project names to avoid silently producing corrupt Bengali text. The failing regression test remains in the suite; the issue must be fixed and Bengali visual rendering, copy/paste, pagination and font embedding verified on supported browsers and operating systems before enabling Bengali reports. An English PDF downloaded in headless Chromium was checked for its PDF signature and extractable title and project name with PDF.js; its visual rendering, diagrams, copy/paste and other viewers remain unverified. The generated diagrams are not to scale and have no authoritative map source. PDF and MapLibre are lazy-loaded but add significant download weight.

PDF diagnosis: the installed fontkit layout of `ভূমি` yields glyph code points in visual order `ভ`, `ূ`, `ি`, `ম`; PDFKit associates the subset glyph ID with those code points in the ToUnicode map. Reusing glyph IDs and complex-script clusters means simply reversing a mapping or changing the expected text is not a reliable general solution. A supported shaping/extraction strategy must preserve both correct visual positioning and logical Unicode across clusters and viewers.

An independent headless Chromium print-to-PDF experiment using both the bundled variable font and a static Noto Sans Bengali font still produced incomplete or corrupted Bengali extraction in PDF.js. This is not evidence of correct visual rendering or of behavior in other viewers, and does not justify enabling Bengali reports. The 5,000-coordinate limit is covered at the report-definition boundary (5,000 accepted; 5,001 rejected). A synthetic 5,000-coordinate English PDF was rendered in Node and downloaded through headless Chromium; all coordinates were extracted in order with PDF.js. Chromium also rejected an attempted 5,001-coordinate report without changing the saved projects. This does not verify visual layout or physical mobile-device performance at the limit.

### Bengali PDF candidate evaluation

An independent research-only trial of [`bangla-pdf`](https://github.com/zamansheikh/bangla-pdf) 0.2.2 with `pdf-lib` 1.17.1, the bundled font and PDF.js 6.4.299 improved extraction of the isolated word `ভূমি`, but produced spurious spaces inside words and incorrect ordering for `অসংখ্য ক্ষুদ্র স্থাপত্য`. It was not integrated or shipped. The package's own documentation also notes PDF.js limitations with complex clusters. This candidate requires replacement of the existing PDFKit-based layout and still needs exact logical text and visual/copy-paste tests before use.

To reproduce the probe without adding production dependencies, from the repository root run `npm ci`, then `npm install --no-save --package-lock=false bangla-pdf@0.2.2 pdf-lib@1.17.1`, followed by `node scripts/evaluate-bengali-pdf.mjs`. A nonzero exit means one or more exact strings did not survive extraction, which is currently expected. The probe does not verify visual shaping, pagination, accessibility or any other PDF viewer. Restore the normal dependencies with `npm ci` afterwards.

English multi-page PDF extraction has a regression test for all 150 coordinates in a sample line, its disclaimer and its project name. Measurement values are rounded to at most three decimals in the report; coordinates are rounded to at most six, which is now stated explicitly. This does not verify visual pagination or copy/paste in supported PDF viewers.

A separate [experimental complex-text PDF implementation](https://github.com/stemlen/bloompdf/pull/7) describes shaping with HarfBuzz, logical-text mappings and zero-width carriers to work around PDF.js diacritic handling. Its merged PR targets Devanagari and Arabic, not Bengali; it was reviewed as a possible research direction, not integrated or tested here. The repository license endpoint did not provide a license, so no code was copied. Bengali-specific extraction, shaping, line wrapping, font licensing, accessibility and supported viewers would all need independent verification before adopting any approach.

A second research-only trial of `jspdf-fontkit` 0.0.7 with the bundled font was run against the same seven sample strings using PDF.js. Only the Bengali digit string was extracted exactly; the six phrases included reordered characters or spurious spaces. No code or dependency was integrated. Reproduce from the repository root with `npm ci`, then `npm install --no-save --package-lock=false jspdf-fontkit@0.0.7` and `node scripts/evaluate-jspdf-bengali.mjs`; the probe exits nonzero on any mismatch. Restore dependencies with `npm ci`. This checks extraction only, not visual shaping, viewer compatibility or suitability of the dependency for production.

### Independent PDF inspection (2026-10-29)

The production report path still uses pdfmake 0.3.13 → PDFKit 0.20.2 → fontkit 2.0.4 with the SIL OFL 1.1 Noto Sans Bengali variable font. Its visual glyph order is mapped into ToUnicode, so the text layer can be wrong even when a page looks plausible. The downloadable Bengali path remains disabled and English downloads still require an ASCII project name. No candidate was integrated.

A reproducible Node fixture builds the **actual report definition**, with a 150-coordinate line spanning three pages, via `node scripts/generate-pdf-review.mjs /tmp/land-pdf-review`. MuPDF extracted all 150 coordinates in order in both languages, detected an embedded font, non-image pages, vector paths and text boxes within page bounds. English title, name and disclaimer checks passed. Bengali title, mixed-language name and reference checks failed; the command exits nonzero. The generated PNGs were inspected for this sample's first page and continuation page, but that is not a language-expert visual validation of all glyphs or proof of correct layout in other renderers. Coordinates are a bulleted list, not a table; no table rendering has been implemented or verified. Bounding boxes inside the page do not prove no overlap or correct page-break semantics.

The BSD-3-Clause `bangla-pdf` 0.2.2 candidate targets Node >=18 and uses HarfBuzz (via MIT-licensed `harfbuzzjs`) and `pdf-lib`; a Node 22 probe generated a PDF, but browser/TypeScript integration and maintenance suitability are not established. As of this inspection its repository was created in September 2026 and was not archived. It was tested independently as follows (the Node PDF.js probe is expected to exit nonzero):

```sh

node scripts/evaluate-bengali-pdf.mjs /tmp/land-bangla-probe.pdf
/tmp/land-pdf-venv/bin/python scripts/inspect-bengali-probe.py /tmp/land-bangla-probe.pdf
```

PDF.js extracted exactly 2/7 sample phrases; MuPDF's exact-line checks passed 3/7, while the full ordered line corpus failed, with split and duplicated fragments. MuPDF detected an embedded font and no raster images. A temporary local experiment using zero-width carrier mappings also failed both extractors and was discarded. A visual rendering of the candidate sample was inspected, but was not independently verified against a shaping reference or by a Bengali typography expert. The candidate is therefore not a verified solution. Chromium print-to-PDF had already failed extraction in the earlier experiment; additionally, a browser-only SPA cannot invoke server-side Puppeteer without a separate service. The added strict seven-case PDF.js regression test deliberately remains failing rather than weakening the requirement.

## Practical backup and recovery guidance

1. Save completed work as a copy; unsaved editor contents are not in backups. Download a backup and retain a separate copy securely. Backup files are unencrypted and may contain sensitive land information. A download event or format check does not prove the file was retained or is authentic.
2. Use Check backup file to validate a chosen file and preview conflicting IDs. The check performs no restore; conflicts can change before a later attempt. For more than 100 projects or 10 MiB, use individual backups where each copy fits the individual limit.
3. Test recovery in a separate browser profile or device before relying on a backup. Select the file, confirm restoration, then open the recovered copies and compare geometry and attributes with the originals. Existing IDs cause the entire restore to fail; do not delete existing records merely to force a restore.
4. If storage is unavailable, a write fails or unreadable records appear, preserve the browser profile and any files. Do not clear browser data. Back up readable copies individually if possible and securely retain the non-restorable diagnostic. Seek help before attempting recovery; this application has no migration or repair feature for unreadable records.

A headless Chromium test injects a `QuotaExceededError` on the second IndexedDB add during restore, verifies the whole transaction rolls back and an unrelated copy remains, then removes the fault and successfully retries. A second Chromium test closes an isolated browser context, restores its downloaded single-copy backup in a fresh context, and verifies the reopened geometry; this is not a test of every browser’s private mode. Component tests simulate blocked storage and quota errors to check that prior copies and form input remain available. This is fault injection, not a real browser quota-exhaustion or private-mode test.

Automated axe-core WCAG 2 A/AA and 2.1 A/AA checks were run on the saved-project screen and its rename form in English and Bengali at 320 and 1366 pixels in headless Chromium. Contrast and accessible-label defects found by those checks were corrected. Automated scans do not verify keyboard-only map drawing, screen-reader usability, other states, other browsers or WCAG conformance.

A Chromium test also rejects deliberately malformed UTF-8 in GeoJSON, backup checking and backup restore without importing or restoring altered data. This rejects invalid encodings, not malicious but valid data; backup validation does not authenticate the source.

## Future schema migration and recovery plan

This is a design constraint for a future schema, **not an implemented migration or repair tool**. Schema 1 and backup version 1 remain unchanged. Do not introduce plot metadata or attachments until their format, limits, privacy and portability have been specified.

Before a future release changes the stored project format:

1. Define and validate both the old and new schemas and backup formats, with explicit version dispatch. Preserve IDs, coordinates, units and timestamps exactly; never silently discard unrecognized fields. Reject unknown future versions and keep the original bytes/records intact.
2. Make and independently verify a secure backup before migration. If any records cannot be backed up, stop and preserve them; the existing diagnostic is not a restorable backup. Do not instruct users to clear storage to fix a migration.
3. Implement a deterministic, tested conversion with a user-visible preview and a rollback/recovery path. Apply changes atomically; abort the transaction on any invalid record, conflict, interruption or quota failure. Do not overwrite a changed record from another tab. Handle blocked IndexedDB upgrades explicitly.
4. Maintain import of supported version-1 backups, with clear behavior for duplicate IDs and newer backups. Define downgrade behavior before release: older app versions may not understand new records and must never rewrite or delete them. Keep the original verified backup until recovery has been tested.
5. Test representative and maximum-size data, unreadable and future-version rows, interrupted upgrades, concurrent tabs, quota failures, old-backup restore and downgrade in each supported browser and platform. Record actual results and limitations before enabling migration.

Current recovery remains the documented backup/restore and diagnostic workflow; no automatic migration, unreadable-record repair, or attachments support exists today.
